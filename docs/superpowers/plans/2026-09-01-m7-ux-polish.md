# UX Polish Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Fix the highest-impact rough edges in the landing → signup → connect → dashboard → chat flow: missing error/loading states that leave a dead-end crash page on any API failure, silent-failure destructive actions, a placeholder browser tab title, and a login flow that doesn't tell first-time users what to expect. This is a punch-list plan, not a redesign — every task is a small, contained fix.

**Architecture:** `apps/web` is Next.js 15 App Router. Server components (`Overview`, `Spending`, `Subscriptions`, `Consents`, `Memory`) call `apiGet` (`apps/web/src/lib/apiClient.ts`) directly and currently have no `error.tsx`/`loading.tsx` anywhere under `apps/web/src/app/dashboard/`, so any backend hiccup or slow response has no graceful UI — Next's default (unstyled) error boundary or a frozen page is what users actually see today.

**Tech Stack:** Next.js 15 App Router conventions (`error.tsx`, `loading.tsx` special files), existing `@/components/ui/*` primitives (Button, Card), Tailwind.

## Global Constraints

- Keep `pnpm --filter @switch/web typecheck` clean after every task (no test suite exists for `apps/web` today — visually verify each change in the browser per this project's own standing rule for UI work).
- Reuse existing UI primitives (`Button`, `Card`, `buttonVariants`) — don't introduce a new component library or styling approach.
- Don't redesign anything not listed in a task below — this plan is deliberately narrow.

### Task 2: Add `error.tsx` and `loading.tsx` for the dashboard route group

**Why:** Every dashboard page (`Overview`, `Spending`, `Subscriptions`, `Consents`, `Memory`) is a server component that `await`s `apiGet`, which throws a raw `Error` on any non-2xx response. With no `error.tsx` anywhere under `apps/web/src/app/dashboard/`, one flaky backend call is a dead-end, unstyled crash page with no retry — and with no `loading.tsx`, navigating between tabs shows nothing until the whole page resolves.

**Files:**
- Create: `apps/web/src/app/dashboard/error.tsx`
- Create: `apps/web/src/app/dashboard/loading.tsx`

- [ ] **Step 1: Build the error boundary**

`error.tsx` must be a client component (`'use client'`) per Next.js convention, receiving `{ error, reset }` props. Show a friendly message ("Something went wrong loading this page.") plus a "Try again" button calling `reset()`, styled with the existing `Card`/`Button` primitives to match the rest of the dashboard.

- [ ] **Step 2: Build a shared loading skeleton**

`loading.tsx` should render a lightweight skeleton (a few muted-background `Card`-shaped placeholder blocks) roughly matching the Overview page's layout — it's shown for every dashboard route during the server-render wait, so keep it generic rather than page-specific.

- [ ] **Step 3: Verify in browser**

Temporarily break `apiGet` (e.g. point `NEXT_PUBLIC_API_BASE_URL` at a wrong port) to confirm `error.tsx` renders instead of Next's default crash screen, then restore it and confirm `loading.tsx` flashes briefly on a hard navigation between tabs (throttle network in DevTools if it's too fast to see locally).

- [ ] **Step 4: Commit**

```bash
git add apps/web/src/app/dashboard/error.tsx apps/web/src/app/dashboard/loading.tsx
git commit -m "ux: add error boundary and loading skeleton for the dashboard route group"
```

### Task 3: Fix silent failures and add a confirm step on RevokeButton/DeleteMemoryButton

**Why:** `apps/web/src/app/dashboard/consents/RevokeButton.tsx` and `apps/web/src/app/dashboard/memory/DeleteMemoryButton.tsx` never check `res.ok` — a failed revoke/delete just stops the spinner with no explanation, looking like a silent no-op. Neither has a confirm step before an irreversible, destructive action (revoking bank access / deleting a memory).

**Files:**
- Modify: `apps/web/src/app/dashboard/consents/RevokeButton.tsx`
- Modify: `apps/web/src/app/dashboard/memory/DeleteMemoryButton.tsx`

- [ ] **Step 1: Read both files in full**

Confirm their exact current fetch/state-handling shape before editing.

- [ ] **Step 2: Add `res.ok` checks and inline error text**

In both components, check `res.ok` after the fetch; on failure, set an error string in local state and render it inline (reuse whatever inline-error style pattern already exists elsewhere, e.g. `ConnectFlow.tsx`'s `text-destructive` usage — see Task 4 below for consolidating this into one shared component).

- [ ] **Step 3: Add a confirm step before the destructive action fires**

Wrap the actual fetch call in a native `confirm()` with a specific message ("Revoke access to <bank name>? Switch will stop seeing new transactions from this account." / "Delete this memory? This can't be undone.") — a native `confirm()` is fine at this project's scale, no need for a custom dialog component.

- [ ] **Step 4: Verify in browser and commit**

Manually trigger a failure (e.g. revoke a consent id that no longer exists, via stale state) and confirm the error text appears instead of a silent stall; confirm the confirm-dialog appears before the real action.

```bash

git commit -m "ux: surface errors and confirm before destructive revoke/delete actions"
```

### Task 5: Clarify the login "check your email" and connect "pending approval" states

**Why:** Login's "sent" state (`apps/web/src/app/login/page.tsx`) says "Check your email for a sign-in link" with no guidance on what happens next (the link opens in a new tab, this tab needs no further action) and no way to detect that the user already signed in elsewhere. The connect flow's pending step (`ConnectFlow.tsx`) says "Approve the consent request to continue" without explaining that this is the user's own bank/AA app, roughly how long it takes, or what happens if they click "check status" before actually approving.

**Files:**
- Modify: `apps/web/src/app/login/page.tsx`
- Modify: `apps/web/src/app/dashboard/connect/ConnectFlow.tsx`

- [ ] **Step 1: Improve login's "sent" copy and add cross-tab detection**

Update the "sent" state's copy to something like: "Click the link in that email — it opens in a new tab and signs you in there. You can close this tab once you see the dashboard." Then, using `supabase.auth.onAuthStateChange` (already available via `getSupabaseBrowserClient()`), listen for a `SIGNED_IN` event on this same tab and `router.replace('/dashboard/connect')` if it fires — covers the case where the user opens the magic link in the same browser/tab context rather than a fresh one.

- [ ] **Step 2: Improve the connect flow's pending-approval copy**

Update the pending state's text to explain this opens the user's own Account Aggregator app/portal to approve, roughly how long it usually takes for a sandbox, and what "I've approved — check status" does. If the user clicks it before actually approving, the current behavior is to silently stay in the pending state — add explicit inline feedback ("Still pending — make sure you approved in the other tab, then try again") rather than nothing happening visibly.

- [ ] **Step 3: Verify in browser and commit**

Walk through both flows end to end once each.

```bash
git add apps/web/src/app/login/page.tsx apps/web/src/app/dashboard/connect/ConnectFlow.tsx
git commit -m "ux: clarify login and connect-flow pending states for first-time users"
```
